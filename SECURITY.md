# RUX security (experimental)

RUX is currently an **experimental language/runtime**. The generated CRUD is **not yet suitable for sensitive production workloads** or multi-user applications. In particular, it does not currently provide end-user login, sessions, per-record authorization, encryption in transit, or an independently audited security model.

## Secure runtime defaults

- The native CRUD binds to `127.0.0.1:3000` by default.
- Remote binds require an explicit opt-in, `RUX_ALLOWED_HOSTS`, and either a configured legacy API token or at least one active identity in `RUX_AUTH_MODE=identities`.
- All HTTP routes are rate-limited by **TCP peer IP**, defaulting to **120 requests/minute** (`RUX_RATE_LIMIT_PER_MINUTE`). At a reverse proxy, peer IP is usually the proxy's address, not the end user's address: enforce per-client limits at the gateway too.
- JSON bodies are capped at **32 KiB**.
- **Legacy mode** uses shared write (`RUX_API_TOKEN`) and optional read-only (`RUX_API_READ_TOKEN`) Bearer tokens.
- **Identities mode** uses independent per-identity Bearer tokens with `reader`, `editor` and `admin` roles. Token **hashes**, not plaintext tokens, are stored in SQLite. Identity credentials can be revoked immediately. They are **API identities**, not end-user login sessions.
- `/metrics` is disabled by default. It requires `RUX_EXPOSE_METRICS=true` and a legacy write token or an admin identity.
- Host headers are checked against explicitly allowed names, and browser cross-origin writes are rejected. CORS remains closed; no external origin is allowed by default.
- Common response-hardening headers are set. HTTPS/TLS is **not implemented by RUX itself**; provide TLS at a trusted reverse proxy or ingress.

## Local development

```powershell
cargo run --release -- dev teste/main.rux
```

Local CRUD is deliberately unauthenticated for development and must not be exposed to untrusted users. Do not store sensitive information in development fixtures.

## Deployment configuration

Create a random secret on a trusted machine and store it securely; do not commit it, embed it in the frontend, or put it in a public log:

```powershell
cargo run --release -- secret generate
```

Example PowerShell configuration for an application behind an HTTPS-terminating reverse proxy:

```powershell
$env:RUX_ENV = "production"
$env:RUX_HOST = "0.0.0.0"
$env:RUX_ALLOW_UNAUTHENTICATED_REMOTE = "true"
$env:RUX_ALLOWED_HOSTS = "api.example.com"
$env:RUX_API_TOKEN = "<random-generated-secret>"
$env:RUX_RATE_LIMIT_PER_MINUTE = "600"
cargo run --release -- start teste/main.rux
```

The legacy variable `RUX_ALLOW_UNAUTHENTICATED_REMOTE` permits **remote binding**, not anonymous remote API access: the runtime still requires a write token. This switch will be renamed in a future release.

**The configuration above is illustrative, not a production-readiness guarantee.** Use TLS, hardened ingress rules, a secret manager, network segmentation, and tested backup/recovery procedures. The generated browser UI does not yet implement user login for token-protected APIs.

## Per-identity API authorization (early access)

Create the native SQLite database once by running the project locally, then stop it:

```powershell
cargo run --release -- run teste/main.rux
```

Create identities using the app output directory (for `app teste`, this is `teste/`):

```powershell
cargo run --release -- identity create teste local_admin admin
cargo run --release -- identity create teste client_reader reader
cargo run --release -- identity list teste
```

The `create` command prints the API token exactly once. Store it in a secret manager, not in source control or frontend JavaScript. Enable identity enforcement:

```powershell
$env:RUX_AUTH_MODE = "identities"
cargo run --release -- start teste/main.rux
```

All native `/api/` operations now require a valid `Authorization: Bearer rux_...` credential. A `reader` can list records, an `editor` can list/create/update them, and an `admin` can also delete records and view metrics (if enabled). Revoke compromised credentials locally:

```powershell
cargo run --release -- identity revoke teste client_reader
```

In `identities` mode, **do not configure** `RUX_API_TOKEN` or `RUX_API_READ_TOKEN`. The runtime refuses to start if the identity table contains no active credentials. Existing local development behavior is unchanged when identity mode is not enabled.

**Limitations:** there is no browser login yet. The autogenerated browser UI does not know how to authenticate in identity mode. This mode is currently intended for controlled API clients, accessed through HTTPS. It does not implement row-level permissions, sessions, password hashing, user recovery, MFA, or tenant isolation. Never expose tokens to browser scripts or commit them to files.

## Native browser login and sessions (experimental)

The new `RUX_AUTH_MODE=users` implements locally provisioned user accounts with Argon2id password hashes, 8-hour revocable sessions, HttpOnly/SameSite=Strict cookies, CSRF tokens for modifying requests, and three roles.

1. Start the CRUD once in local mode (creates its SQLite file), then stop it:

   ```powershell
   cargo run --release -- dev teste/main.rux
   ```

2. Create an administrator **locally** without putting a password on the command line:

   ```powershell
   cargo run --release -- user create teste admin_local admin
   ```

   Enter and confirm the password using the hidden prompts. At least 12 UTF-8 bytes are required.

3. Enable session authentication, and start the app again:

   ```powershell
   $env:RUX_AUTH_MODE = "users"
   cargo run --release -- dev teste/main.rux
   ```

4. Open http://127.0.0.1:3000. The generated frontend now shows a login form. A reader can only list records, an editor can list/create/update records, and an admin can also delete records.

5. Manage accounts:

   ```powershell
   cargo run --release -- user list teste
   cargo run --release -- user disable teste admin_local
   ```

   Disabling a user immediately invalidates existing sessions. There is **no** self-registration endpoint or password-reset feature yet. Provision accounts directly on the trusted server/administrative machine.

For automated provisioning, `rux user create <project> <username> <role> --password-stdin` reads one line from standard input rather than accepting secrets as command-line arguments. Never commit passwords, store them in shell history, or print them in build logs.

### Security boundaries

- The user's browser sends a cookie, not an API token. Authentication and role checks happen on the server for **every** API operation; JavaScript-only restrictions are not a security boundary.
- The frontend includes CSRF tokens for state-changing requests. The browser cookie is not accessible to JavaScript. The generated script is restricted by a Content Security Policy hash.
- Remote browser login requires `RUX_ALLOWED_HOSTS`, an explicit remote bind opt-in, and `RUX_TLS_TERMINATED_AT_PROXY=true` **only after** deploying HTTPS termination and blocking public direct access to the backend. The switch is an operator assertion, not a TLS verifier.
- On remote or production deployments, session cookies have the `Secure` attribute. Use HTTPS at the reverse proxy. A raw HTTP backend exposed directly to the internet is not a supported secure deployment.
- This is not yet a multi-tenant security system. **Records are still shared by all authenticated users of the same CRUD app.** Roles are checked per operation, not per record or organization. Do not expose customer-separated or other sensitive workloads until row-level authorization and independent review are implemented.
- The CLI user database is SQLite-specific. Other database backends and login providers are not implemented yet.
- The legacy, identities and users modes are separate. Do not leave shared API tokens in the environment when using `RUX_AUTH_MODE=users`.

## Security limitations / planned work

1. Harden the new browser-user login: MFA, password recovery, trusted TLS-provider integration, session policies and security review.
2. Declarative RBAC/ABAC, per-record and tenant isolation with deny-by-default semantics.
3. Secret providers/rotation and first-class TLS/deployment integration.
4. Dependency auditing, fuzzing, adversarial integration tests and external security audit.
5. Migration away from the legacy generated JavaScript server, which is local-only and does not share the native Rust authorization middleware.

## Reporting security issues

Do not post working exploits or sensitive data in public issues. Contact the repository maintainer privately to report suspected vulnerabilities.
